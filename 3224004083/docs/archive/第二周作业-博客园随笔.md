## 二、计算模块接口的设计与实现过程

### 2.1 需求拆分与代码组织

程序按"入口 → 读文件 → 规范化 → 算相似度 → 写答案"拆成 5 个模块 + 1 个入口。
每个模块只做一件事，**文件读写不进入相似度函数**，这样算法可以脱离磁盘独立测试：

```text
main.py                 命令行入口：参数校验、流程编排、统一异常转换与退出码
plagiarism/
├── errors.py           四类可预期错误的异常定义
├── reader.py           文件读取、编码识别、HTML 噪声剥离
├── normalize.py        文本规范化（去空白/标点、统一大小写）
├── similarity.py       核心算法：字符 n-gram 多重集 Dice 加权融合
└── writer.py           答案格式化（两位小数）与写出
tests/                  71 个单元测试
tools/                  样例生成、批量验收、性能分析
```

程序流程：

```text
接收三个路径
    ↓
参数个数 ≠ 3 ──────────────→ 打印用法，退出码 2
    ↓
读取两份文本（UTF-8 → GB18030 → UTF-16 依次尝试）─ 失败 → 提示，退出码 1
    ↓
规范化（去空白标点、统一大小写、剥 HTML 噪声）
    ↓
有效字符为空 ──────────────→ 提示"没有可比较的有效文本"，退出码 1
    ↓
统计 1~4 阶字符 n-gram 频次 → 逐阶算 Dice → 加权平均
    ↓
格式化为两位小数写入答案文件 ─ 失败 → 提示，退出码 1
    ↓
退出码 0
```

### 2.2 关键接口

| 接口 | 职责 | 返回 |
|---|---|---|
| `main(argv) -> int` | 参数校验、串联全流程、把异常转成退出码 | 进程退出码 |
| `read_text(path) -> str` | 按编码读文件、去 BOM、NFKC、剥离 HTML 噪声 | 文本 |
| `normalize(text) -> str` | 只保留字母、数字与汉字，字母转小写 | 规范化文本 |
| `count_ngrams(text, n) -> Counter` | 统计相邻 n 字符片段的频次（多重集） | 频次表 |
| `dice_overlap(a, b) -> float` | 两个频次表的多重集 Dice 系数 | `[0,1]` |
| `ngram_similarity(orig, copied) -> float` | 多阶加权融合 | `[0,1]` |
| `compute_similarity(orig_path, copied_path) -> float` | 按路径计算重复率 | `[0,1]` |
| `write_answer(path, score) -> None` | 两位小数写出，带换行 | 无 |

### 2.3 文本规范化

规范化要抹掉的是**格式差异**，留下的是**内容差异**，所以只保留字母、数字与汉字，
其余（空白、换行、标点、符号）一律丢弃：

```text
输入：今天是星期天，天气晴。\n 晚上 看电影
输出：今天是星期天天气晴晚上看电影
```

这样"只改标点"或"只改换行"不会影响查重结果。在读取阶段还会做两件事：

1. **Unicode NFKC 归一化**，把全角 `ＡＢＣ１２３` 转成半角 `ABC123`；
2. **HTML 噪声剥离**——评测样例里有部分内容是从网页上抓下来的，夹带了
   `<html>/<div>/<script>`、`&nbsp;` 之类的样板。不去掉这些噪声，正文明明相同
   的两份文件也只能算出 0.6 左右的相似度。实测剥离后，同一份内容 + 网页外壳
   的相似度从 0.60 左右回到 **0.99**。

### 2.4 核心算法：字符 n-gram 多重集 Dice

**第一步，切 n-gram。** 中文没有天然分词边界，直接用相邻的 n 个字符当"指纹片段"：

```text
文本 A：甲乙丙丁      →  2-gram 特征：甲乙、乙丙、丙丁
文本 B：甲乙丙戊      →  2-gram 特征：甲乙、乙丙、丙戊
```

**第二步，统计频次（多重集而不是普通集合）。** 用 `Counter` 记次数，
`aaaa` 里的 `aa` 出现 3 次，重复段落的权重不会被抹平。

**第三步，Dice 系数。** 设两个文本中片段 g 的频次分别是 `A(g)`、`B(g)`：

```text
overlap = Σ_g min(A(g), B(g))
Dice    = 2 × overlap / (|A| + |B|)
```

上例中 overlap = 2，两个文本各 3 个 2-gram，所以 `Dice = 2×2/6 = 0.67`。
完全相同 → 1，完全不重合 → 0，天然落在 `[0,1]`。

**第四步，多阶加权。** 短片段对局部改写敏感，长片段更能体现稳定内容、对无关文本
更有区分度，所以把 1~4 阶的 Dice 按下面的权重融合：

| n | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 权重 | 0.10 | 0.20 | 0.35 | 0.35 |

**关于"乱序"为什么不用特殊处理**：n-gram 频次是**全文统计量**，天生与顺序无关。
把段落顺序打乱，片段的多重集几乎不变，所以相似度依然很高——这正是作业里
"能处理段落顺序发生变化的相似内容"要求的。反过来，如果有人把每句话内部的分句
顺序也打乱，局部片段会被破坏，分数就会下降，这与人的直觉一致。

### 2.5 算法行为验证

用 `tools/run_samples.py` 对 10 类样例批量验收（原文 586 字符）：

| 样例 | 改动方式 | 相似度 |
|---|---|---|
| orig_1.0 | 与原文完全一致 | **1.0000** |
| orig_1.0_html | 正文相同，外面包了一层网页样板 | **0.9926** |
| orig_0.8_syn | 术语换成近义词（改） | 0.9353 |
| orig_0.8_dis_1 | 每个段落内部句子旋转（乱序） | 0.9746 |
| orig_0.8_dis_2 | 全部句子整体打乱（乱序） | 0.9328 |
| orig_0.8_dis_3 | 句子内部的分句顺序颠倒（乱序） | 0.9094 |

| orig_0.8_del | 删除约 20% 句子（删） | 0.8671 |

### 2.6 复杂度

设原文长度 m、抄袭版长度 n，总长度 N = m + n：

| 阶段 | 时间复杂度 | 空间复杂度 |
|---|---|---|
| 读取与规范化 | O(N) | O(N) |
| n-gram 统计（n = 1~4） | O(N) | O(N) |
| 逐阶 Dice（哈希表求交） | O(N) | O(N) |
| **整体** | **O(N)** | **O(N)** |

注意这里是**线性**复杂度，而不是编辑距离或 LCS 那种 O(m×n)。这也是它能在一秒
内处理 55 万字符的原因。

## 三、计算模块接口部分的性能改进

### 3.1 第一版实现与热点定位

第一版能跑通，但把 `normalize` 写成了最直的逐字符循环：

```python
def normalize(text):
    return "".join(_keep(ch) for ch in text)   # 逐字符回调 Python
```

用 `cProfile` 剖析 55 万字符的大输入，热点分布如下：

| 函数 | 调用次数 | tottime 占比 |
|---|---|---|
| `_keep`（规范化里的单字符判断） | 1 124 930 | **25.3%** |
| `Counter._count_elements` | 8 | 22.7% |
| `<genexpr>`（切 n-gram） | 4 098 824 | 17.5% |
| `str.join` | 2 | 5.5% |
| `unicodedata.category` | 1 124 930 | 3.4% |

也就是说：**真正算相似度的代码并不慢，慢的是"给每个字符做一次 Python 函数调用"**。
`_keep` 一个函数就吃掉四分之一的时间，加上它内部的 `isdigit` / `isupper` /
`unicodedata.category`，规范化调用链合计约 **60%**。

### 3.2 改进措施

**改进一：规范化改成「查表 + `str.translate`」。**
把"字符 → 目标字符"的映射缓存起来，交给 C 层的 `str.translate` 完成：

```python
_TRANSLATION: dict[int, str] = {}          # 进程内共享的字符映射表

def _translation_for(text: str) -> dict[int, str]:
    for ch in set(text):                   # 只为新出现的字符建表
        code = ord(ch)
        if code not in _TRANSLATION:
            _TRANSLATION[code] = _keep(ch)
    return _TRANSLATION

def normalize(text: str) -> str:
    return text.translate(_translation_for(text))
```

中文文章里不同字符只有几千个，缓存命中率接近 100%，所以建表成本是一次性的，
后续每次调用几乎只剩纯 C 开销。

**改进二：一阶 n-gram 走 C 层快速路径。**

```python
if n == 1:
    return Counter(text)        # 直接用 C 实现，跳过生成器与切片
```

**改进三：超长文本自动降阶。** 超过 80 万字符时不再统计 4-gram，超过 200 万
字符时只保留 2、3 阶，用可控的精度损失换取内存与时间的安全边界。

### 3.3 改进效果

同一台机器、同一份 55 万字符输入，规范化耗时：

| 实现方式 | 耗时 | 相对提速 |
|---|---|---|
| 改进前：逐字符 Python 循环 | 0.214 s | 1.00× |
| 改进后：查表 + `str.translate` | 0.071 s | **3.02×** |

![规范化改进前后耗时对比](【发博客前请把这张图上传并替换成本地链接：docs/normalize_compare.png】)

改进后重新剖析，热点已经转移到了算法本身：

| 函数 | tottime 占比 |
|---|---|
| `Counter._count_elements`（统计频次） | 47.1% |
| `<genexpr>`（切 n-gram 片段） | 38.0% |
| `unicodedata.normalize`（NFKC） | 9.0% |
| `str.translate`（规范化） | 2.8% |

![热点函数柱状图](【发博客前请把这张图上传并替换成本地链接：docs/perf_chart.png】)

**这一步的结论很重要**：不要凭算法直觉去优化，先用剖析工具确认热点在哪。
我原本以为瓶颈会在 Dice 的集合求交上，实际测出来是规范化。

### 3.4 不同规模的时间与内存

规模档位用样例原文复制放大构造，抄袭版做了"打乱 + 删除 15%"的改动；
每个档位跑 5 次取中位数，内存用 `tracemalloc` 记录峰值：

| 规模档位 | 原文（字符） | 抄袭版（字符） | 耗时中位数 | 峰值内存 |
|---|---|---|---|---|
| 小 | 5 541 | 4 724 | **12.9 ms** | 0.2 MiB |
| 中 | 55 386 | 47 074 | **83.1 ms** | 0.7 MiB |

即便是 55 万字符的大文本，也在 **1 秒内、10 MiB 以内**完成，距离评测的
5 秒 / 2048 MB 限制有很大余量。运行时间与文本长度基本呈线性关系，
和 2.6 节的复杂度分析一致。

## 五、计算模块部分异常处理说明

评测环境把"异常退出"视为失败，所以程序内部所有可预期的错误都转成自定义异常，
由 `main` 统一捕获、打印提示，并用非零退出码结束，**绝不把 Python 堆栈抛给评测机**。

| 异常 | 设计目标 | 触发场景 | 当前处理 | 退出码 |
|---|---|---|---|---|
| 参数个数错误 | 阻止参数越界 | 只给 1、2、4 个参数 | 打印用法 | 2 |
| `FileReadError` | 输入不可用 | 文件不存在、路径是目录、无权限 | 提示并保护已有答案 | 1 |
| `FileReadError` | 编码不可识别 | UTF-8 / GB18030 / UTF-16 全部失败 | 提示已尝试的编码 | 1 |
| `EmptyTextError` | 没有可比较文本 | 空文件、纯标点文件 | 提示"没有可比较的有效文本" | 1 |
| `AnswerWriteError` | 输出不可写 | 答案是目录、上级目录不存在 | 提示并拒绝写入 | 1 |
| `OSError` | 兜底的系统错误 | 磁盘/权限等意外 | 统一提示 | 1 |

关键测试断言：

```python
def test_argument_count_four(self) -> None:
    code, _ = self._run([str(self.original), str(self.copied),
                         str(self.answer), "extra"])
    self.assertEqual(code, EXIT_USAGE_ERROR)

def test_punctuation_only_file_returns_error(self) -> None:
    punct = self.tmp / "punct.txt"
    punct.write_text("。。。！！！", encoding="utf-8")
    code, _ = self._run([str(self.original), str(punct), str(self.answer)])
    self.assertEqual(code, EXIT_RUNTIME_ERROR)

def test_open_failure_is_wrapped(self) -> None:
    with mock.patch("builtins.open", side_effect=OSError("设备不可用")):
        with self.assertRaises(FileReadError):
            read_text(str(path))
```

另外还有一条容易忽略的边界：**答案文件不能指向输入文件**，否则一次误操作就会把
原文覆盖掉。当前实现通过"失败时保持已有答案文件不变"来规避（见 4.2 的用例 ④）。

## 六、总结

### 6.1 已完成

* 命令行查重程序，零第三方依赖，支持 UTF-8 / GB18030 / UTF-16 与中英混排；
* 核心算法：1~4 阶字符 n-gram 多重集 Dice 加权融合，时间与空间复杂度均为 O(N)；
* 十类样例批量验收通过：完全一致 1.00、乱序 0.91~0.97、增删改 0.87~0.94、无关 0.02；
* 71 个单元测试全部通过，语句覆盖率 100%；
* 用 cProfile 定位到热点是规范化，改用查表 + `str.translate` 后**提速 3.0 倍**；
* 55 万字符输入耗时 0.996 s、峰值内存 7.1 MiB，远低于 5 s / 2048 MB 限制；
* 六类可预期错误全部转成退出码，不抛出未捕获异常。

### 6.2 不足与后续改进

1. 相似度是**字面相似度**，不理解语义。"星期天"和"周天"不会被认为是同一个词，
   要处理这类同义改写需要引入词向量或分词+同义词表；
2. 输出是一个整体比例，**不能定位到具体段落**。下一步可以在此基础上加一个
   "按句对齐"的步骤，输出被判定为重复的句子区间；
3. 当前把两份文件完整读进内存，不是流式算法。虽然 500 万字符以内都没问题，
   但如果将来要处理书籍级别的文本，需要改成流式读取 + 分块指纹；
4. n-gram 的权重（0.10/0.20/0.35/0.35）是手工设定的，缺少标注数据来做验证。
   如果能拿到课程提供的标准答案，可以用一份小规模网格搜索确认这组权重是否合适。
