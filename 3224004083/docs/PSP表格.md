# PSP 表格

学号：**3224004083**　　项目：**第一次个人编程作业 —— 论文查重**

> **填表规则**（PSP 的本意）：
> 「预估耗时」必须在**动手写代码之前**填写；「实际耗时」必须在**整个项目做完之后**回填。
> 提前填实际耗时，就失去了 PSP 用来对照"估得准不准"的意义。

合计：预估 520 分钟（≈8 小时 40 分），实际 665 分钟（≈11 小时 5 分）。

## 二、这份预估是怎么来的

不是拍脑袋填的，按"任务清单 → 逐项估时"推出来：

| 要做的事 | 对应 PSP 阶段 | 估时 |
|---|---|---|
| 读懂需求、确认评测约束、查一遍同类写法 | Analysis | 40 |
| 确定算法、画模块关系与流程 | Design Spec + Design | 70 |
| 定命名与注释规范、复审设计 | Design Review + Coding Standard | 30 |
| 写读文件 / 规范化 / n-gram / 余弦 / 写答案 | Coding | 120 |
| 自己复审一遍代码 | Code Review | 30 |
| 写至少 10 个用例、跑覆盖率、补异常分支 | Test | 100 |
| 整理测试结论与覆盖率截图 | Test Report | 40 |
| 统计代码量、PSP 回填、写博客 | Size Measurement + Postmortem | 60 |

其中最容易低估的是 **Analysis**：作业里有几条硬约束（5 秒、2048 MB、不联网、
不读写其他文件、不能异常退出）会反过来影响算法选型与异常设计，必须先把它们吃透。

## 三、偏差分析（预估 vs 实际）

| 阶段 | 预估 | 实际 | 偏差 | 原因 |
|---|---:|---:|---:|---|
| Analysis | 40 | 55 | +15 | 要确认几条硬约束如何影响算法与异常设计 |
| Coding Standard | 15 | 25 | +10 | 引入 pylint 后回头统一命名与文档规范 |
| Design | 40 | 45 | +5 | 模块边界调整了一轮（读写与算法彻底分离） |
| Coding | 120 | 150 | +30 | 多阶 n-gram 的权重调参反复试了几轮 |
| Code Review | 30 | 35 | +5 | 复审时发现问题要重新跑一遍测试 |
| Test | 100 | 160 | +60 | 为把覆盖率补到 100%，额外覆盖异常分支与进程入口 |
| Test Report | 40 | 45 | +5 | 覆盖率图与性能图都重绘了几次 |
| Postmortem | 45 | 60 | +15 | 性能分析发现瓶颈不在算法而在规范化，多花时间做对照实验 |
| **合计** | **520** | **665** | **+145** | 超支主要在两块：**把边界想全**、**用数据确认优化方向** |

## 四、结论

1. **Coding 只占总时间的 22%**（150 / 665）。真正花时间的是测试（160 分钟）和其他
   质量环节——这和 PSP 想让人意识到的"写代码只是工程的一部分"是一致的。
2. 我明显低估了 **Test**（100 → 160）。为了把语句覆盖率补到 100%，需要专门去覆盖
   "编码全部失败""以子进程启动入口"这类分支，成本比预估高得多。
3. 还有一个"计划外"的收获：在做性能分析时做了一次 A/B 对照实验，推翻了先前
   "关闭分代 GC 能提速 2.2 倍"的错误结论（实为机器负载漂移）。这一步花了约 15 分钟，
   但它避免了把噪声当成优化成果写进报告。
